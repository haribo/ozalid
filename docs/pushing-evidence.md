# Pushing evidence

How a project gets its captures into ozalid.

There is no CLI ([ADR 0015](adr/0015-no-cli-clients-call-the-api.md)): a client
calls the API. This document carries the sequence and the reasoning. Field
names, status codes and exact shapes live in `apps/server/api/openapi.yaml`,
which is the contract — nothing here restates it
([ADR 0009](adr/0009-documentation-strategy.md)).

A worked example lives in `apps/web/e2e/fixture.ts`: about a hundred and forty
lines of TypeScript doing everything below. It is worth reading before writing
anything, and it cannot rot silently — the end-to-end suite runs it in CI on
every pull request.

## What a client is, and is not

ozalid knows no test runner ([ADR 0003](adr/0003-runner-and-tracker-agnostic-boundaries.md)).
It never reads a repository, never watches a pipeline, never calls anything of
yours. Every fact it holds arrives because a client sent it.

So the client is yours to write, and it is small: hash some files, make one or
two HTTP calls, remember a few identifiers.

## Once, when a project starts

**An operator bootstraps the instance.** One command on the machine mints the
first administrator, the project, a service account and its token. The token is
printed once and never again — only its hash is kept, so a lost one is replaced
rather than recovered.

**The client creates its cases and keeps the ids.** A case's identity is
generated by ozalid, not chosen by you
([ADR 0014](adr/0014-server-generated-case-identity-and-catalogue-tree.md)):
titles change, identity must not. Create each case once, store the id it
returns beside the test it belongs to, and use that id forever after. A client
that re-creates its cases every run produces a catalogue that grows and a
history that resets.

## Every run

**Hash every capture.** The address of a capture is the sha256 of its bytes,
written `sha256:` followed by sixty-four hex characters. Content is stored under
that address ([ADR 0004](adr/0004-content-addressed-capture-storage.md)), so two
runs producing the same screen produce the same address and the bytes are stored
once.

**Build the manifest.** It names each case by its id, its steps in order, and for
each step the captures with the variant they were taken in.

Then get the bytes and the manifest to the server. There are three ways, and
they differ only in how much they send.

### The simple way

Upload every capture, then push the manifest. Five lines, and what the worked
example does.

It sends every capture's bytes on every run, including the ones the store
already holds — which the server accepts and discards. On a suite of a dozen
captures that costs nothing worth measuring.

### The frugal way

Push the manifest **first**. If the store lacks some of the bytes, intake refuses
and **names exactly the addresses it is missing**. Upload those, push the same
manifest again, and it is accepted.

The refusal is not an error to endure — it is how a client learns what to send.
One round trip tells it everything, where asking capture by capture would cost
one per capture. On a run where nothing changed, the first push simply succeeds
and no bytes move at all.

This is the way to grow into. A suite of two hundred captures where three moved
sends three images instead of two hundred.

### The middle way

Ask whether the store holds an address, one at a time, and upload only what is
missing. It sends as little as the frugal way and asks far more often. It is
worth it only when uploading is expensive and asking is cheap — rarely.

## What a capture must be

**A PNG.** A lossy format re-encodes the same screen into different pixels every
run, which makes "has it changed?" unanswerable, so intake refuses anything else
(`design/product.md` §2).

**Taken in one environment.** Two machines rendering the same screen produce
different bytes — different font rasterisation, a scrollbar of another width. A
capture therefore declares the environment that produced it, and is only ever
compared against what was approved in that same environment
([ADR 0017](adr/0017-a-reference-belongs-to-an-environment.md)). Declare it, and
keep it stable: changing the string means starting the comparison over.

**Complete.** Every step is expected to carry a capture for every variant the
run declares for that case. A gap is a failed run, and ozalid shows it as one
([ADR 0016](adr/0016-a-case-is-complete-or-it-says-so.md)).

## Variants are whatever you declare

ozalid ships no list of axes. A variant is a combination of axis values —
`theme: dark`, `viewport: mobile`, `locale: fr`, or anything a project cares
about. They exist because a manifest mentioned them, and a project that reviews
one rendering declares no axis at all.

An axis a capture does not mention is simply absent from its variant: a site with
no dark mode has no theme axis, rather than a theme axis with one value.

## Recordings are optional

A video of the run can be attached to an edition. It is viewable, and it is
never compared: encoding is not deterministic, so a video can prove nothing
about its own freshness ([ADR 0013](adr/0013-a-recording-is-not-a-capture.md)).
A case without one is a normal case.

## What the token reaches

One project. A token naming project A cannot push to project B, and the attempt
is refused rather than ignored
([ADR 0018](adr/0018-an-actor-is-never-invented.md)). A client pushing to two
projects holds two tokens.

Send it as a bearer token on the two endpoints that write: pushing an edition,
and uploading bytes. Everything else needs nothing today — see
`design/product.md` §8 for where that is going.

## What ozalid will never do

It will not open an issue on your tracker
([ADR 0003](adr/0003-runner-and-tracker-agnostic-boundaries.md)). When a
reviewer's comment becomes an issue, the client tells ozalid the issue's id, url
and title; ozalid stores them and links to them. It never authenticates against
a tracker and never creates anything there.

It will not decide a case's state either. States are computed from the facts
recorded ([ADR 0002](adr/0002-server-owns-the-review-lifecycle.md)), and no
endpoint accepts one as an argument.
